# relay-bench：Claude API 中转站掺水检测

拿来测你手里的 Claude 中转到底掺没掺水：是不是真 Opus、智商有没有打折、缓存是不是真的、钱算得对不对，还有短请求根本测不出来的那种——**上下文一长就偷偷删掉中间的内容**。

一个 Python 文件，只用标准库，不用装任何依赖。可以同时测好几个站，跑完会出一张对比表。

最省事的用法：

```bash
cp config.example.json config.json   # 填地址和 key
python3 relay_bench.py check -y      # 每站大约 $3（按官方价算）
```

## 一、文件结构

```
relay-bench/
├── relay_bench.py         # 主脚本（只依赖 Python 标准库，不用 pip 安装任何东西）
├── config.example.json    # 配置模板
├── README.md              # 本文件
├── .gitignore             # 忽略 config.json 和 results/，防止 key 和结果被误提交
└── results/               # 运行后自动生成，每次运行一个带时间戳的子目录
```

## 二、环境要求

- Python 3.8 及以上（macOS 和 Linux 自带的 `python3` 即可）
- 能访问被测中转站的网络
- 被测站点需兼容 **Anthropic Messages API**（`POST /v1/messages`）
- 默认参数是为 Claude Opus 5.x 设计的（adaptive thinking、`effort` 档位）。测其他模型见第九节“局限性”。

## 三、快速开始

```bash
cd relay-bench
cp config.example.json config.json      # 1. 复制配置
# 2. 编辑 config.json，填入站点地址和 key（见第四节）
python3 relay_bench.py probe            # 3. 先跑基础探测（几乎不花钱），确认连通
python3 relay_bench.py check -y         # 4'. 推荐：掺水体检，每站约 $3 官方价，出一张红黄绿结论表
python3 relay_bench.py all              # 4. 常规全套，每站约 $1.6 官方价
python3 relay_bench.py all --heavy      # 5. 需要时再加长上下文三项，每站约 $9 官方价
```

每项测试跑完，都会在终端打印一张对比表。全部结果保存在 `results/<时间戳>/`：
- `summary.md`：可读的汇总报告；
- `<测试名>.json`：每次请求的完整原始数据，包括模型原文、usage 和响应头；
- `verdict.md`：**体检结论表**（✅ 通过 / ⚠️ 可疑 / ❌ 实锤），多站并排，可以直接贴到帖子里。

### check：掺水体检（推荐）

`check` = `probe + auth + iq + cache + trunc --control`，是能回答“有没有掺水”的最便宜组合：

| 掺水手法 | 由哪项抓 |
|---|---|
| 偷塞系统提示词、按你的钱计费 | probe |
| 老模型/小模型冒充 | auth（知识截止、分词器指纹）+ iq |
| 没设缓存也按写入价收 | cache（E） |
| **超过 20 万 token 删掉中间、照样按全量计费** | trunc（带阈值下对照） |

可选：在 config.json 里加 `"fingerprint_ref": <数字>`（拿官方 key 跑一次 auth 得到的分词器指纹），之后各站指纹会自动和它比对。

## 四、配置说明（config.json）

| 字段 | 说明 | 默认值 |
|---|---|---|
| `model` | 要测的模型 ID（每个站点也可以单独指定 `model`） | `claude-opus-5-5` |
| `budget_usd_per_site` | **单站点单次运行的预算上限**（按官方价折算的美元）。达到上限后，该站点后续请求全部停止 | 15 |
| `settle_seconds` | 每项测试结束后，等多少秒再读余额。中转站通常先预扣、后结算，读得太早会不准 | 8 |
| `balance_path` | 用量查询接口路径。new-api / one-api 系的中转站一般都支持；填 `null` 则不读余额 | `/v1/dashboard/billing/usage` |
| `balance_divisor` | 用量接口返回值要除以多少，才换算成“额度单位”。new-api 返回的是“分”，所以是 100 | 100 |
| `price_per_mtok` | 官方价（美元 / 百万 token），用来折算“官方价”和“计费倍率”。官方调价后要同步修改 | Opus 5.5 官方价 |
| `sites[]` | 站点列表：`name`（自定义名称）、`base_url`（不带 `/v1`）、`api_key` 或 `api_key_env`（从环境变量读取 key） | — |

**关于 key 的安全**：推荐用 `api_key_env`，例如 `export RELAY_B_KEY=sk-...`，这样 key 不会落盘。`config.json` 已写进 `.gitignore`。分享这个文件夹之前，请确认 `config.json` 不在里面。

## 五、命令与参数

```bash
python3 relay_bench.py <测试名...> [选项]
```

| 测试名 | 测什么 | 每站官方价（默认参数） |
|---|---|---|
| `probe` | 基础探测 | ≈ $0.001 |
| `auth` | 真实性 / 满血 / 功能完整性 | ≈ $0.05 |
| `iq` | 10 道推理题 | ≈ $0.25 |
| `effort` | effort 参数是否生效 | ≈ $0.15 |
| `speed` | 首字延迟、生成速度、并发 | ≈ $0.15 |
| `longout` | 长输出完整性、输入 token 虚增 | ≈ $0.65 |
| `cache` | 5 种缓存写法的命中率、TTL、自动注入 | ≈ $0.35 |
| `longconv` | 长对话（20 轮，约 39 万 token） | ≈ $4（暂停那一轮若缓存过期，再加约 $2） |
| `boundary` | 阈值两侧对照 | ≈ $3.3 |
| `trunc` | 长上下文截断检测 | ≈ $1.5（加 `--control` 再加约 $0.8） |
| `check` | 掺水体检：probe+auth+iq+cache+trunc(带对照) | ≈ $3 |
| `all` | 等于前 7 项 | ≈ $1.6 |
| `all --heavy` | 全部 10 项 | ≈ $11 |

**实际扣费 = 官方价 × 站点倍率**，倍率由 `probe` 之后的每项测试自动测出。预计总价超过 $1 时，脚本会先要求确认；加 `-y` 可以跳过确认。

常用选项：

| 选项 | 作用 |
|---|---|
| `--sites a,b` | 只测指定站点 |
| `--config 路径` | 使用其他配置文件 |
| `--out 目录` | 指定结果目录 |
| `-y / --yes` | 跳过费用确认 |
| `--effort high` | `iq` 使用的 effort 档位 |
| `--questions Q1,Q7` | `iq` 只跑指定题目 |
| `--runs 3 --concurrency 8` | `speed` 的顺序测试次数和并发数 |
| `--sizes 520,780,1500` | `longout` 测哪几个输出长度（行数） |
| `--doc-words 4000` | `cache` 测试用的文档长度（4000 词约 1 万 token） |
| `--threshold 200000` | **怀疑的截断阈值（token 数）**。`longconv`、`boundary`、`trunc` 都会围绕它构造上下文 |
| `--chapter-words 8000` | 长上下文测试里每章的词数（8000 词约 1.94 万 token） |
| `--turns 20 --lookback 7` | `longconv` 的轮数，以及每轮问几章之前的编号 |
| `--pause 370` | `longconv` 最后一轮前暂停多少秒（测缓存 TTL）；设为 0 则不测 |
| `--chapters N` | `trunc` 的章数；0 表示自动取 1.5 倍阈值 |
| `--control` | `trunc` 额外跑一个阈值以下的对照 |

示例：

```bash
python3 relay_bench.py iq speed --sites relayA,relayB               # 只比智商和速度
python3 relay_bench.py trunc --control --sites relayA -y              # 只做截断检测（带对照）
python3 relay_bench.py trunc --threshold 128000 --sites relayA       # 怀疑在 12.8 万 token 处截断
python3 relay_bench.py longconv --turns 10 --pause 0                 # 短一点的长对话，不测暂停
```

## 六、各项测试详解

### 1. probe：基础探测

- **方法**：
  - 读取 `/v1/models`；
  - 发一个最小请求 `"Reply with exactly: OK"`；
  - 试探 `count_tokens` 接口和余额接口；
  - 记录响应头。
- **看什么**：
  - **最小请求的输入 token 数**：官方正常是 13–15。如果明显偏高（比如 139），说明中转站在你的请求前注入了系统提示词。这部分 token 会按你的钱计费，还可能影响模型行为。
  - **响应头**：可以识别中转站的架构（例如 `x-new-api-version` 代表 new-api 系）、号池分组、节点编号等。
  - `model` 字段和 `msg_` 开头的消息 ID：只能作为辅助参考，因为中转站可以伪造。

### 2. auth：真实性 / 满血 / 功能

| 子测试 | 方法 | 判读 |
|---|---|---|
| 系统提示词探测 | 用 4 种问法（原文引用、中文描述、字数、base64 编码）问模型上下文里有没有别的指令；base64 会自动解码 | 能看出注入了什么。回答被截断、掏空或答非所问，也是可疑信号，可能存在输出过滤 |
| system 位置探测 | 在 system 里放一个标记，问模型它出现在哪里、前面还有什么 | 看你的 system 是否被挪动，前面是否被插了别的内容 |
| 知识截止 | 问 2025 年的 4 件事（新教皇、GPT-5 发布时间、Claude 4、Opus 4.5） | Opus 5.x 应该 4/4。如果答不出来，可能是知识截止更早的老模型冒充 |
| **分词器指纹** | 同一段固定文本（代码加中文）的 token 数，减去基础请求的 token 数 | **同一个模型在不同站点，这个数必须完全一致**。不一致，说明分词器不同（换了模型），或 usage 是中转站自己算的 |
| thinking 签名 / 摘要 | 用 adaptive thinking、`display: summarized` 解一道题 | 有签名、有摘要、答对（401），才算正常 |
| strict 工具调用 | 带 `strict: true` 的工具 | 应返回 `{"city": "Paris", "unit": "c"}` |
| 结构化输出 | `output_config.format` 使用 json_schema | 应返回合法 JSON，首都是东京 |
| 图片识别 | 脚本现场生成一张左红右蓝的 PNG | 应答 `LEFT=red RIGHT=blue` |

### 3. iq：推理题

- **方法**：10 道有唯一标准答案的题，答案都已用程序算好。题型包括：铺砖计数、大数取模、数位和计数、ménage 数、概率递推、Python 代码阅读、**写代码**、日期推算、几何、单位根滤波计数。默认 effort=high，5 道并行。
- **写代码题的判题**：从回答里提取模型写的函数，和 400 组随机用例的暴力解对拍，外加一次性能测试。代码会在一个**独立的临时目录里、以隔离模式（`python -I`）运行**，超时 60 秒。
- **判读**：Opus 5.x 正常应接近 10/10。和其他站点对比时，要同时看“思考 token 合计”：同档 effort 下思考量明显偏少，可能是 effort 被改写，也可能是注入的指令要求模型简短作答。

### 4. effort：effort 参数是否生效

- **方法**：同一道难题，分别用 low、medium、high、max、不传 effort 五种设置各跑一次，记录思考 token 数。
- **判读**：正常情况下，max 的思考量应明显高于 low（脚本按超过 1.5 倍判定）。如果几档差不多，说明 effort 参数可能被中转站丢弃或改写了。单次采样有波动，要看整体趋势。

### 5. speed：速度

- **方法**：顺序生成 3 篇约 600 词的短文，测首字延迟和正文生成速度；再用 8 路并发测稳定性。
- **指标**：
  - **首字延迟**：从发请求到第一个正文 token 的时间；
  - **正文生成速度**：(输出 token − 思考 token) ÷ (总时长 − 首字延迟)。
- **判读**：
  - 生成速度是模型本身的特征，可以当“指纹”辅助判断有没有换模型：小模型通常明显更快。
  - 首字延迟主要反映中转链路的开销。
  - 并发失败多，说明号池容量不足或有限流。

### 6. longout：长输出

- **方法**：让模型逐行输出 1 到 N 的英文写法（默认 520、780、1500 行，约 0.6 万到 1.9 万 token）。
- **判读**：
  - **是否完整**：看是否输出了全部 N 行，且停止原因是 `end_turn`。被截断说明中转站限制了输出长度。
  - **输入 token 是否虚增**：三个请求的 prompt 几乎一样长，输入 token 应该基本相同。如果长输出那一个的输入凭空多出几万 token（脚本会标 ⚠），说明中转站可能在拼接多次上游调用，把已生成的内容重新当作输入计费。

### 7. cache：缓存

用同样的方法依次测 5 种写法。每个文档都带本次运行的随机标识，避免命中上次运行留下的缓存。

| 写法 | 典型用途 | 正常表现 |
|---|---|---|
| A 固定 system + 每次换问题 | 客服、RAG、批量处理 | 第一次写入，之后每次读取，命中率约 75% 以上 |
| B 长文档放用户消息第一个块 + 每次换问题 | 文档问答 | 同上 |
| C 固定 system + 同一个问题 | 重复请求 | 第二次命中 |
| D 多轮对话（顶层自动缓存） | Claude Code、聊天 | 命中率随轮数累积上升 |
| E 完全不设缓存 | 只发一次的请求 | **不应出现**任何缓存写入或读取 |

**常见异常**：
- **A 为 0%**：中转站删掉了你在 system 上设的缓存断点，或把断点挪到了请求末尾。结果每次都按写入价重写，比不用缓存还贵。
- **B 为 0%**：用户消息里非最后一块的缓存断点没有生效。
- **E 出现了写入**：中转站自动给你加了缓存，按写入价收费。只发一次的请求等于多付 25%（5 分钟 TTL）到 100%（1 小时 TTL）。
- **TTL 为 1h**：写入价是输入价的 2 倍，好处是缓存保留 1 小时。TTL 为 5m 时，停顿超过 5 分钟缓存就会失效。

### 8. longconv：长对话

- **方法**：默认 20 轮，每轮追加一“章”，约 1.94 万 token，章节正中间埋一条 `FACT-k: vault code ... XXXXXX`。每轮问 7 章之前的编号，要求只答编号。缓存断点放在最新消息末尾（和 Claude Code 的做法一致），完整历史（含 thinking 块）每轮都传回去。最后暂停 6 分钟，再问第 1 章，用来测缓存 TTL。
- **熔断**：连续 2 轮缓存命中率低于 50% 就自动停止，防止上下文很大时缓存失效导致费用失控。另外还有单站预算上限兜底。
- **判读**：
  - **阈值以下和以上的召回正确率**：如果在某个整数附近断崖式下跌，比如 20 万以下 10/10、以上 2/10，就要怀疑截断，接着跑 `trunc` 确认。
  - **缓存命中率**：正常会随轮数上升到 90% 以上。
  - **暂停后的那一轮**：5 分钟 TTL 的站点会全部重写；1 小时 TTL 的站点应该命中。

### 9. boundary：阈值两侧对照

- **方法**：围绕 `--threshold` 构造 5 个请求：
  - R0：小上下文基准；
  - R1：约 0.78 倍阈值，不设缓存；
  - R2：约 1.26 倍阈值，不设缓存；
  - R3：略低于阈值，设缓存；
  - R4：在 R3 的对话后面续一章，跨过阈值，设缓存。

  每个请求都包含：召回 5 个编号（每章单独一行作答，避免评分错位）、3 道难题、写一篇约 500 词的故事（用来测生成速度）。同时记录响应头里的节点、分组、渠道等信息。
- **判读**：
  - **阈值两侧推理正确率和生成速度一致**：说明没有换模型。
  - **阈值以上召回出现 NOTFOUND**：说模型“找不到”，而不是答错一个数字，通常说明那段内容没送到模型那里。
  - **R4 的缓存读取等于 R3 的全部内容**：只要模型实际收到的内容被改动过（例如中间被删），这个“完整命中”就不可能是上游真实返回的。
  - **R1、R2 出现缓存写入**：说明中转站自动注入了缓存。
  - **节点标识变化**：可能走了不同的线路。

### 10. trunc：截断检测（决定性测试）

- **方法**：一次发约 1.5 倍阈值的上下文（默认 15 章、约 29 万 token），让模型**逐章列出它能看到的标题和编号**，说明缺了哪些章，并描述文本断裂处（句子编号跳号、中途断开、插入的标记等）。加 `--control` 时，会再跑一个阈值以下的对照。
- **判读**：
  - **整章消失**，并且模型描述了“文本中途断开”或“出现 `[...]` 标记”：可以证实是截断，因为测试用的原文里不存在 `[...]`。
  - **对比“计费的上下文 token”和“实际可见章节”**：被删的内容如果照样计费，这就是最直接的证据。
  - 所有章节都在、只是个别编号答错：属于模型的注意力问题，不算截断。

## 七、计费核对原理

1. 每项测试前后各读一次用量接口，两次相减得到“实际扣费”（额度单位）。
2. 按每次请求返回的 usage 和官方价，算出“官方价折算”（美元）。
3. **每 $1 官方价扣费 = 实际扣费 ÷ 官方价折算**。这就是站点的实际计费倍率。比如充值 1 元得到 1 个额度单位，倍率 1.40 就表示官方价 $1 的用量在这里花 1.4 元。

**判读**：
- 各项测试的倍率应该基本稳定。
- 某一项明显偏高，说明这类请求被多收了钱，比如 usage 虚增或缓存价不对。
- 前一两项偶尔偏低或偏高，可能是结算延迟，看后面几项即可。

**注意**：usage 是由中转站转发的，**它可以伪造**。所以“倍率稳定”只说明它按自己报的 usage 计费，不代表 usage 本身是真的。要核实真假，得靠行为测试：分词器指纹、召回、截断检测。

## 八、结果解读速查表

| 现象 | 可能原因 | 用哪项测试确认 |
|---|---|---|
| 最小请求输入 token 远高于 15 | 注入了系统提示词 | probe、auth（系统提示词探测） |
| 分词器指纹和其他站点不同 | 换了模型，或 usage 是中转站自己算的 | auth |
| 知识题答不出 2025 年的事 | 老模型冒充 | auth |
| 推理题得分低、思考量明显偏少 | effort 被改写、换了小模型、注入了“简短作答”指令 | iq、effort |
| 生成速度异常快 | 换了小模型 | speed、boundary |
| 长输出不完整 | 输出长度被限制 | longout |
| 长输出时输入 token 凭空多出几万 | 拼接多次上游调用，按输入重复计费 | longout |
| system 缓存命中率为 0 | 缓存断点被删除或挪到末尾 | cache |
| 不设缓存也被按写入价收费 | 自动注入缓存 | cache（E） |
| 召回在某个阈值以上断崖下跌 | 长上下文被截断 | longconv，再用 trunc 确认 |
| 模型说“找不到”，或复述出 `[...]` 标记 | **中间内容被删除** | trunc |

## 九、局限性与注意事项

1. **只能从外部观测**。中转站返回的 usage、`model` 字段、消息 ID 都可能被改写。所以结论要以**模型行为**（推理、召回、速度、是否看见内容）为准，账单数字只作辅助。
2. **单次采样有随机性**。思考量、首字延迟等指标波动较大，关键结论建议重复跑几次，或者多个站点同时跑对比。
3. **长上下文测试较贵**，而且费用随 `--threshold` 和 `--chapter-words` 线性变化。如果怀疑的阈值不是 20 万，直接改 `--threshold`，章节数会自动换算。
4. **token 经验值**：每章 token 数按“每词约 2.43 token”估算，这是 Opus 5.x 分词器的经验值。换了模型后，实际 ctx 会以 usage 为准，章节数可能需要手动调整（`--chapters`）。
5. **测其他模型**：
   - 需要不支持 `output_config.effort` 或 adaptive thinking 的模型时，要改脚本里对应的请求参数；
   - 官方价要在 `price_per_mtok` 里改成对应模型的价格；
   - 知识题的标准答案也要按该模型的知识截止调整。
6. **余额接口**只适用于 new-api / one-api 系的中转站。不支持时，“实际扣费”会显示“无法读取”，其他测试照常进行。
7. **写代码题会在本机执行模型生成的代码**。虽然已经在临时目录、隔离模式下运行并设了超时，但对于不信任的站点，如果有顾虑，可以用 `--questions Q1,Q2,Q3,Q4,Q5,Q6,Q8,Q9,Q10` 跳过 Q7。
8. 每次运行会生成随机标识写进缓存类测试的文本，所以重复运行不会被上一次的缓存影响。
